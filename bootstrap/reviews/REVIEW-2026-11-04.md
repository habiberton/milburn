# Milburn PRD/ARCH review: v1 (as specified and as built) and v2 drafts

Date: 2026-11-04. Branch `review/prd-arch-2026-11-04`, based on `origin/main` at
`e4b4987` (MB-012 merged), with `PRDv2.md` and `ARCHv2.md` copied from `design/v2-draft`
(`d67063a`). Local only: nothing is pushed, and the build agent's checkout is not touched.

Judged against the stated goal: **Milburn is an agent distro that orchestrates software
development across harnesses and works as a software factory.**

## Verdict

The authority model is sound and worth keeping. It has three parts: agents propose,
a deterministic controller decides, and every external effect is journaled and
idempotent. The specs and the code apply it consistently.

The plan around that core has three serious problems:

1. **v1 cannot ship software.** No path exists from a passed issue to code on a branch
   that anyone else can use (B1).
2. **The agent process model contradicts itself in code** (B2). Nothing has run end to
   end, so nobody has noticed (B3).
3. **v2 builds in the wrong direction for the goal.** The goal says "across harnesses",
   and both versions defer that. v2 instead spends its budget on discovery, design,
   OpenSpec, and phone access (M1).

## Blocking findings

### B1. No delivery path, and dependent issues build on a base without their dependencies

- PRD §1 says Milburn owns "delivery".
- PRD §5 excludes merging. PRD §17 defers pull-request automation.
- ARCH §14 limits the credential to issue read/write and excludes repository-content
  write.
- The Coder rule `role_rules/coder/completion.md` says "Never push, merge, or open a pull
  request."
- So when QA passes, the controller closes the issue while the code sits on a local
  branch, `milburn/issue-<n>`. No component pushes it, integrates it, or opens a PR.
- The scheduler readies issue B when issue A is `done`. The worktree manager builds B
  from a caller-supplied `base_sha`, and no component defines that SHA as one containing
  A's code. Either B is built without A, or the base question is silently left to
  whoever wires the scheduler.
- V2-30 ("archive after the pull request is merged") depends on a PR that v1 never
  creates.

A factory whose finished work never leaves the workshop is not a factory. v1 needs a
defined integration target (decision Q1).

### B2. The Codex process model contradicts itself in code

- `CodexAdapter.launch` runs `codex exec --json -`
  (`src/milburn/agents/codex_adapter.py:170`). That is a one-shot, non-interactive run
  that takes its prompt from stdin and exits.
- `TmuxRuntime.send_doorbell` steers by typing a token plus Enter into the pane
  (`src/milburn/runtime/tmux.py:272`). That only works for an interactive TUI that is
  reading the keyboard.
- The persistent Coordinator chat (PRD §6.1, ARCH §12.1) also assumes an interactive
  session.

These cannot all be true at once. A doorbell sent to an `exec` process does nothing.

Codex 0.166 (installed here) has the right primitives:

- `codex exec resume <id>`: continue a session for another turn.
- `codex queue`: queue a message for an existing session.
- `codex app-server`: a daemon with structured events.
- `--output-schema`: enforce the shape of the final result.
- `--json`: JSONL events.

The structured channel is the control plane. tmux becomes, at most, a place for a human
to watch. The question also matters for every future harness: Claude Code exposes
`-p --output-format stream-json --resume` and an Agent SDK, not a keyboard protocol.
Decision Q2.

### B3. Twelve product tasks are merged and nothing runs end to end

- The CLI supports only `--version` (`src/milburn/app/cli.py`).
- `Controller.handle` validates a command and appends one event. No composition root
  wires the store, adapter, runtime, registry, and scheduler together.
- The first end-to-end proof is MB-016, the last task.
- So far: about 9.4k source lines and 10k test lines, at about 25M tokens per task
  (handoff estimate). The work went into horizontal layers with exhaustive fault
  handling (generation fencing, amendment freezes, usage reconciliation) before one real
  request ever went through.
- B2 is what this ordering produces: integration contradictions surface last, when they
  cost the most.

Decision Q3: build a walking skeleton next.

## Major findings

### M1. The multi-harness goal is deferred by both v1 and v2

- The seam is Codex-shaped. Its names are `CodexAdapter` and `codex_adapter.py`, and its
  launch, steer, and collect semantics follow the Codex CLI.
- PRD §17 already sketches the right v2: a role-to-harness/model/effort table that fails
  closed when an assignment is unavailable, and review on a different model or harness
  than the author.
- v2 instead adds discovery, design, OpenSpec, observability, and remote/phone access:
  about 48 requirements and 30 acceptance criteria, and nothing for a second harness.
- Cross-harness review is the most direct quality gain a multi-harness distro offers.
  The Tester runs on a different harness than the Coder, so the same model's blind spots
  are not shared. Decision Q5.

### M2. Bootstrap governance has leaked into the product spec

Several v1 requirements are lessons from running the bootstrap coordinator, written up
as product features:

- §12.3 plan amendments, which freeze all dispatch until a remote merge is reconciled.
- Handoff manifests with inbox/outbox sequence numbers.
- The four-rule rework escalation.

Each one is defensible on its own. Together they give the PRD 31 acceptance criteria and
about 50 event types for a product that has not yet run one request. A factory user
mainly needs "pause new work and ask me". They do not need a merged-PR revision gate
before dispatch resumes. Decision Q6.

### M3. The Classifier/Router is an LLM doing a lookup table's job

- ARCH §4's transition table maps almost every input to exactly one role.
- Launching a Codex process in its own tmux window to propose what the table already
  decides costs tokens, adds latency, and adds a failure mode, and the guard throws away
  any proposal that differs from the table anyway.
- v2 adds more to it: `design_required` and discovery skip.
- The genuinely open classification questions (bug, feature, or chore? user-facing?) fit
  one structured call by the Planner or Coordinator using `--output-schema`.

Decision Q4.

### M4. Throughput of one

- ARCH §5.9 allows one active Coder globally, and PRD §17 defers parallel Coders.
- A factory is measured by throughput. Most of the isolation is already built: per-issue
  worktrees, ownership leases, and idempotent effects.
- What is missing is B1's integration branch. Once that exists, running independent
  issues in parallel is mostly a scheduler limit. It belongs in the first increment after
  the skeleton, ahead of most of v2.

### M5. The target repository's CI is not the ground truth

- PRD §4.8 grants check reads, but no component uses them.
- The Tester runs commands and reports evidence, so completion rests on an agent's
  account of a test run.
- Once B1 pushes branches, required CI checks on the pushed SHA should be a completion
  precondition. That is cheap, deterministic, and harness-independent.

### M6. Each persistent LLM process is a running cost

- The Coordinator is a long-lived Codex session that has no authority and is woken for
  every actionable event.
- It is valuable as the user's chat surface. It should be the only persistent model
  session, and it should start fresh from the bounded state digest (§12.4) rather than
  accumulate context.
- The spec already allows this. The tmux-window mandate (B2) works against it.

## Minor findings

- **GitHub through MCP.** The gateway is 667 lines plus a tool-schema compatibility
  check (ARCH §13), all to call about six REST operations. It is built, so keep it. Do
  not extend the MCP dependency to PRs and checks without comparing it against `gh` or
  REST.
- **Six skills.** There are six Codex-specific skill directories under `.agents/skills`.
  The `SKILL.md` format is shared with Claude Code (V2-18), which is good. The install
  path and loading mechanism are per harness and belong in the harness adapter.
- **`delivery_posture`** is a required field on `RequestEnvelope` with no defined values
  or behavior. It is the natural place to hang the Q1 decision.

## v2-specific findings

- **V-a. Four overlapping artifacts.** The DiscoveryBrief, the plan, PRD/ARCH, and the
  OpenSpec proposal plus deltas all say "what and why". V2-25 ("each document has one
  job") does not hold, because the brief *is* the proposal and PRD.md is also the
  narrative. Folding Discovery into Planning (as a gate on the Planner, with the grill
  ledger) removes one role and one artifact. Open question 1 in PRDv2 leans this way.
- **V-b. OpenSpec cost against use.** You decided against forking, and that stands. Even
  so, Milburn uses OpenSpec's layout and validation while removing its tasks artifact,
  apply step, and skills, and it takes on in return:
  - a dependency on Node 22.12 or a standalone build;
  - schema commands marked experimental;
  - JSON output with no documented contract;
  - IDs derived from names, which break on rename and need an alias table.

  If any of the PRDv2 §12 item-4 checks fail, the fallback should be Milburn's own
  requirement and scenario format with explicit stable IDs, keeping OpenSpec's file
  conventions. That fallback is small.
- **V-c. Observability should follow the harness channel.** Most of the "Needs
  validation" items in V2-35/36 resolve on their own once B2 is settled. `codex exec
  --json` and the app-server emit structured events, so activity ingest reads the
  control channel instead of scraping session logs.
- **V-d. Remote/phone has the largest risk-to-value ratio.** A cheap first step is
  read-only monitoring plus decision answers, served on loopback and reached over a
  private network the user provisions (for example Tailscale). Pairing, scopes, push,
  and the transcript store can wait until that has been used. V2-37 also relaxes a v1
  non-goal, which needs an explicit amendment.
- **V-e. The stage table (D2-1) is the best idea in v2.** Pair it with the
  role-to-harness table: a stage declares its role, and the role table declares harness,
  model, and effort. That is the distro's core configuration surface. Do it in the
  multi-harness increment.
- **V-f. Design stage.** Valuable for UI products, and expensive: four variants per
  screen with rendered screenshots. It is reasonable as a later stage-table entry, and
  it is not on the critical path to a factory.

## Process observation

At about 25M tokens per task, with 95% in the main session, Milburn's own build is the
best available data on what a software factory costs. v1 makes budgets a non-goal, which
is fine. The per-task usage report (PRD §12.7) should still be treated as a first-class
product output, because "tokens per merged issue" is the factory's unit economics.

## Direction decisions (2026-11-04, from the user)

Context: the user's original goal is an agent distro in the spirit of an
existing open-source project, which is inspiration only; its terminology is not
used. Milburn keeps its own vocabulary: Coordinator (the agent the user talks
to), role agents (Coder, Tester, ...), tasks, and built-in processes.

1. **Controller shape:** the deterministic controller becomes a `milburn`
   enforcement CLI plus event store that the Coordinator calls. The Coordinator
   holds judgment. The CLI holds what a script can check, the independent QA
   gate and completion policy, journaled GitHub/PR effects and merge authority,
   and the event record.
2. **Task types** are configurable data, named and added or removed later. The
   spec task type defaults to OpenSpec. Specs are written only when the user
   asks, or inside a built-in process the user chose.
3. **Delivery modes** per project: `local-only`, `pr` (default, the user
   merges), `auto-merge` (only after independent QA passes).
4. **Harnesses:** the Coordinator runs in Claude Code or Codex, and role agents
   in either. By default the Tester runs on a different harness from the Coder;
   this is configurable.
5. **Build agent:** stops after MB-013 until PRD/ARCH are rewritten for this
   direction.
6. **Built-in processes** are stage tables (ARCHv2 D2-1). Free-form prompts
   stay the default; processes are offered at the start. Initial set: "Start
   from scratch" (discovery and grill, design, OpenSpec spec, issues, parallel
   build tasks, independent QA, delivery), "Add a feature", "Fix a bug". More
   later.
7. **Repository creation in "Start from scratch":** undecided. Add the code
   scaffolding now (a repository stage whose "create" option is a stub behind
   user approval).

Unique aspects kept from Milburn: token and session telemetry (one event store
as the spine), OpenSpec integration, independent QA with no self-approval,
journaled external effects.
